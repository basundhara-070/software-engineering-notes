Software Engineering Notes

SDLC Models

Blueprint-style revision notes — definitions, diagrams & quick recall points.

01 SDLC — Software Development Life Cycle

A defined sequence of stages followed to build quality software.
Memorize: R-D-I-T-D-M → "Real Developers Implement Tests, Don't Miss!"

Note: SDLC is the umbrella process. Waterfall, V-model, Prototyping, Incremental, Evolutionary — all are models (implementations) of this same life cycle.

02 Classic Waterfall Model

Strictly linear — one phase finishes completely before the next starts. No going back.

Advantages

  • Simple, easy to understand & manage
  • Clear milestones & deliverables per phase
  • Works well for small, well-defined projects

Disadvantages

  • No feedback path — can't go back
  • Working software only at the very end
  • High risk if requirements change
Memorize: "No looking back" → strict one-way arrows only.

03 Iterative Waterfall Model

Classic waterfall + feedback loops — a phase can send info back to the previous one.

Advantages

  • Errors can be corrected earlier
  • More flexible than classic waterfall

Disadvantages

  • No early prototype for customer
  • Late changes still costly
Memorize: Same 6 phases as waterfall, but arrows can point backward too.

04 V-Shaped Model

Verification (left, going down) + Validation (right, going up) — every dev phase has a matching test phase.

Advantages

  • Testing planned from day one
  • Defects caught early per phase
  • Good for small, well-understood projects

Disadvantages

  • Very rigid, like waterfall
  • No early working prototype
  • Costly & hard to handle changing requirements
Memorize: "V for Verification & Validation" — left leg builds, right leg tests, each pair mirrors the other.

05 Prototyping Model

Build a quick working sample first, let the customer react, refine, then build the real thing.

Advantages

  • Requirements get clarified early
  • Customer sees & feels the system sooner
  • Reduces misunderstanding of needs

Disadvantages

  • Customer may expect prototype = final product
  • Scope/requirements can keep expanding
  • Extra cost of building throwaway prototypes
Memorize: Gather → Design → Build → Evaluate → Refine (loop) → Final Product.

06 Incremental Model

Whole system split into small increments; each increment is a mini-waterfall delivering a usable piece.

Advantages

  • Early, working (partial) product
  • Easier to test & manage in small pieces
  • Lower risk of total project failure

Disadvantages

  • Needs good upfront planning & open architecture
  • Total cost may exceed single waterfall
Memorize: Requirements are known upfront → just built & delivered in slices.

07 Evolutionary Model

Requirements are NOT fully known upfront — build a version, get feedback, evolve it into the next version.

Advantages

  • Handles changing / unclear requirements well
  • Customer feedback shapes each version

Disadvantages

  • Hard to estimate total cost & time
  • Needs careful management, can drift in scope
Memorize: Incremental = known reqs, sliced. Evolutionary = unclear reqs, versions grow via feedback.

08 Spiral Model

Risk-driven: waterfall + iterative combined. Each loop = one phase, split into 4 quadrants; radius = cost.

Advantages

  • Strong focus on risk analysis at every loop
  • Good for large, complex, high-risk projects
  • Combines benefits of waterfall + prototyping

Disadvantages

  • Expensive — needs risk-assessment expertise
  • Complex to manage; not ideal for small projects
Memorize: 4 quadrants every loop → "Objectives → Risks → Build → Plan", repeat. Bigger loop = more cost.

09 Agile Model

A mindset/set of principles: build in short cycles, deliver working software fast, adapt to change.
4 Core Values (Agile Manifesto): Individuals & interactions over processes & tools · Working software over documentation · Customer collaboration over contract negotiation · Responding to change over following a plan.

Advantages

  • Fast, frequent delivery of working software
  • Welcomes changing requirements, even late
  • Continuous customer & team feedback

Disadvantages

  • Hard to predict final cost/time upfront
  • Needs highly involved, available customer
  • Less documentation can hurt handovers
Memorize: Agile = philosophy. Scrum/Kanban/XP = frameworks that put Agile into practice.

10 Scrum

Most popular framework to implement Agile — organizes work into fixed-length Sprints.

3 Roles

  • Product Owner — owns & prioritizes backlog
  • Scrum Master — removes blockers, guards process
  • Development Team — builds the increment

3 Artifacts

  • Product Backlog — full wish-list of features
  • Sprint Backlog — items picked for this sprint
  • Increment — usable output at sprint end
5 Events: Sprint (the container) → Sprint Planning → Daily Scrum (daily, 15 min) → Sprint Review (demo to stakeholders) → Sprint Retrospective (team improves itself).
Memorize: 3 Roles, 3 Artifacts, 5 Events — Scrum is Agile's most structured framework.

11 Software Requirements

A requirement = a capability or condition the software must meet to satisfy a stakeholder's need.

3-Level View

  • Business requirements — why the project exists (goals)
  • User requirements — what the user needs to do (plain language)
  • System/functional requirements — precise, detailed spec for developers

Sources of Requirements

  • Stakeholders & end-users (interviews, surveys)
  • Business rules & domain knowledge
  • Existing systems & regulations/standards
Memorize: Business → User → Functional — each level gets more detailed & technical.

12 Functional vs Non-Functional Requirements

Functional = WHAT the system does. Non-functional = HOW WELL it does it.
Functional (FR)Non-Functional (NFR)
Describes a feature / behaviourDescribes a quality attribute / constraint
"System shall allow login with email + password""Login must complete within 2 seconds"
"Generate monthly sales report as PDF""System must be available 99.9% of the time"
"Allow admin to add/delete products""Passwords must be stored encrypted (security)"
Verified by testing the feature directlyVerified by measuring performance/quality

Common NFR Categories

  • Performance · Security · Usability · Reliability
  • Scalability · Availability · Maintainability · Portability
Memorize: Functional = verb sentences (action). Non-functional = quality words (fast, secure, reliable).

13 Software Requirements Specification (SRS)

A formal document capturing all functional & non-functional requirements — the contract between client & developer.

8 Characteristics of a Good SRS

  • Correct · Complete · Consistent
  • Unambiguous · Verifiable
  • Modifiable · Traceable · Ranked (by importance)

Typical SRS Structure (IEEE 830)

  • 1. Introduction (purpose, scope, definitions)
  • 2. Overall description (product perspective, users)
  • 3. Specific requirements (functional, interface, performance)
  • 4. Appendices / supporting info
Memorize: SRS answers "what the system must do" — never how it's built internally.

14 User Requirements (with examples)

High-level statements, in plain natural language, describing what the system should do for the user — no technical detail.
User Requirement (plain language)Corresponding Functional Requirement
"Customers should be able to search for books by title, author, or ISBN."System shall provide a search function querying Title/Author/ISBN fields, returning results within 2 sec.
"I want to reset my password if I forget it."System shall send a time-limited reset link to the registered email on request.
"The manager should see today's sales at a glance."System shall render a dashboard widget showing total sales for the current date, refreshed every 5 min.
Memorize: User requirement = what a non-technical stakeholder would say. Functional requirement = the precise engineering translation of it.

15 Data Flow Diagram (DFD) — What & How to Design

A graphical tool showing how data moves through a system — processes, stores, entities & flows. No control flow or timing.

4 Symbols

  • Rectangle — External Entity (source/sink)
  • Circle — Process (transforms data)
  • Open rectangle / two lines — Data Store (data at rest)
  • Arrow — Data Flow (data in motion)

Steps to Design a DFD

  • 1. Identify external entities
  • 2. Identify main processes (system functions)
  • 3. Identify data stores
  • 4. Connect with data flows; start at Context (Level 0), decompose further
Rule: Data can never flow entity→entity or entity→store directly — it must always pass through a process.

16 Levels of DFD — 0, 1, 2 (Example: Food Ordering System)

Each level decomposes a process into finer sub-processes; the picture zooms in but data in/out stays balanced.
Level 0 (Context Diagram) — whole system as ONE process; only external entities + major flows shown.
Level 1 — process 0 split into major sub-processes (1.0, 2.0, 3.0) with data stores.
Level 2 would decompose one Level-1 bubble further — e.g. 2.0 Process Payment → 2.1 Validate Card, 2.2 Authorize Transaction, 2.3 Generate Invoice. Go deeper only where a process is still complex.
Memorize: 0 = whole system · 1 = major functions · 2 = sub-steps of one function. Numbering shows lineage (2.1 belongs to 2.0).

17 Logical vs Physical DFD

Logical = WHAT the business does. Physical = HOW it's actually implemented (people, tech, files).
Logical DFDPhysical DFD
Technology-independent, business-process viewImplementation-specific, shows real tools/tech
"Validate Customer Details""Java module validates input against Oracle CUSTOMER table on App Server"
"Store Order""Insert row into MySQL orders table via REST API"
Used early, for understanding requirementsUsed later, for design & implementation
Memorize: Logical = business logic. Physical = bits, servers, file names.

18 Function-Oriented vs Object-Oriented Design

Two approaches to translate requirements into a software structure.
Function-Oriented (Structured)Object-Oriented
Top-down decomposition into functions/modulesSystem modelled as interacting objects/classes
Data & functions kept separateData + behaviour encapsulated together
Tools: DFD, Structure ChartsTools: UML Class, Object, Sequence diagrams
Low reusabilityHigh reusability (inheritance, polymorphism)
Memorize: Function-oriented = "what functions act on data". Object-oriented = "what objects know & can do".

19 Software Project Management (SPM)

Planning, organizing, staffing, monitoring & controlling a software project to hit scope, time, cost & quality goals.

Key SPM Activities

  • Scope & requirement management
  • Estimation (cost, effort, schedule)
  • Risk management & quality assurance
  • Scheduling, staffing / team organization
  • Monitoring, control & configuration management
Memorize: SPM is the umbrella activity that runs alongside every SDLC phase, start to finish.

20 Risk Identification & Reactive vs Proactive Risk Management

Risk = an uncertain event that, if it happens, negatively affects the project.

Risk Categories

  • Project risks — schedule, budget, resources, staff turnover
  • Technical risks — design flaws, implementation, interfacing
  • Business risks — market shift, losing budget/priority, strategy change
Reactive Risk ManagementProactive Risk Management
"Fire-fighting" — act only after a risk becomes a real problemIdentify & plan mitigation before the risk occurs
No monitoring until crisis hitsContinuous monitoring of risk indicators
Higher cost, higher stressLower cost, controlled response
Memorize: Reactive = react after the fire starts. Proactive = fire drill before it happens.

21 Risk Assessment (with example)

Ranks identified risks by severity so the team focuses on what matters most.
Risk Exposure  RE = P × C
P = probability the risk occurs (0–1)  |  C = cost/loss if it occurs
RiskPC (days lost)RE = P×C
Requirements keep changing0.684.8
Key developer leaves0.3154.5
Server crash0.1202.0
Result: Rank by RE → Requirements change (4.8) > Key dev leaves (4.5) > Server crash (2.0). Tackle the highest RE first.

22 Risk Control vs Risk Mitigation

Mitigation acts BEFORE a risk occurs. Control is the ongoing process of watching & responding throughout the project.
Risk MitigationRisk Control
Proactive step taken in advance to reduce probability/impactOngoing monitoring + executing contingency if risk occurs
Eg: cross-train team members so "key person leaves" hurts lessEg: weekly risk review; if the person actually leaves, execute the pre-planned hiring contingency
One-time preventive actionContinuous activity across the project

4 Risk Control Strategies

  • Avoid — remove the risk's cause entirely
  • Mitigate — reduce probability or impact
  • Transfer — shift risk to a third party (insurance, outsourcing)
  • Accept — acknowledge and absorb it if cost of handling > cost of risk
Memorize: Mitigation = one action, before. Control = umbrella process, during (mitigation is one tool inside it).

23 COCOMO — Basic & Intermediate (with numerical)

COnstructive COst MOdel — estimates effort & time from estimated project size (KLOC).
Basic:  E = a × (KLOC)^b person-months    T = c × (E)^d months
Project Typeabcd
Organic (small, familiar)2.41.052.50.38
Semi-detached (medium)3.01.122.50.35
Embedded (complex, rigid)3.61.202.50.32
Numerical (Basic, Organic, 32 KLOC):
E = 2.4 × 321.05 = 2.4 × 38.05 = 91.3 person-months
T = 2.5 × (91.3)0.38 = 2.5 × 5.56 = 13.9 months
People needed = E / T = 91.3 / 13.9 ≈ 7 people
Intermediate COCOMO adds an Effort Adjustment Factor (EAF) from 15 cost drivers (e.g. reliability, complexity, experience) — each rated Very Low→Extra High with a multiplier; EAF = product of all 15.
E = a × (KLOC)^b × EAF  (coefficients: Organic a=3.2, b=1.05)
Numerical: 32 KLOC, EAF = 1.2 →
E = 3.2 × 38.05 × 1.2 = 146.1 person-months
Memorize: Basic = size only. Intermediate = size × EAF (15 cost drivers). Detailed COCOMO further adjusts per phase/module.

24 CPM & PERT — Numerical

Network technique to find the shortest possible project duration = the Critical Path (longest chain, zero slack).
ActivityPredecessorDuration (days)
A—3
B—4
CA2
DA5
EB, C1
FD, E6
Amber = critical path A → D → F
Path A-D-F = 3+5+6 = 14 days (longest → critical)
Path A-C-E-F = 3+2+1+6 = 12 days
Path B-E-F = 4+1+6 = 11 days
Slack (LS−ES) = 0 only along A, D, F — confirms critical path.
PERT uses 3 estimates per activity: te = (o + 4m + p) / 6, variance σ² = ((p−o)/6)²
A (o=1,m=3,p=5): te=3, σ²=0.444  |  D (o=3,m=5,p=7): te=5, σ²=0.444  |  F (o=4,m=6,p=8): te=6, σ²=0.444
Project te = 3+5+6 = 14 days   Total variance = 0.444×3 = 1.33 → SD = 1.15
P(finish ≤ 16 days): Z = (16−14)/1.15 = 1.73 → ≈ 95.8% probability
Memorize: CPM = one duration (deterministic). PERT = 3 durations (probabilistic) → same network, added uncertainty.

25 Verification vs Validation

Verification: "Are we building the product right?" Validation: "Are we building the right product?"
VerificationValidation
Checks work-products against specificationsChecks the final system against user needs
Static — reviews, walkthroughs, inspectionsDynamic — actually executing/running the software
Done throughout the SDLCDone mainly after building, at delivery
Eg: peer-review the SRS documentEg: acceptance testing with real end-users
Memorize: Verification = documents & design (no code running). Validation = running code in front of the user.

26 Types & Levels of Testing

Types = the technique used. Levels = the stage/scope at which testing happens.

By Technique

  • Black-box — test functionality, no code knowledge
  • White-box — test internal logic/code paths
  • Grey-box — partial knowledge, mix of both

By Purpose

  • Smoke · Sanity · Regression
  • Performance / Load / Stress
  • Security · Usability · Compatibility
Levels of Testing — Unit → Integration → System → Acceptance (widest at the base = most frequent).
Memorize: "U-I-S-A" — Unit tests one module, Integration checks module links, System tests the whole app, Acceptance confirms it meets user needs.

27 Error Seeding (with numerical)

Estimate how many real bugs remain by deliberately planting known "fake" bugs and seeing how many get caught.
Let  S  = total seeded (artificial) errors inserted
    ns = seeded errors found during testing
    nr = real errors found during testing

Total actual errors, N = (nr × S) / ns
Remaining real errors = N − nr
Numerical: 20 seeded errors (S=20). Testing finds 15 of the seeded ones (ns=15) and 6 real bugs (nr=6).
N = (6 × 20) / 15 = 8 total actual errors estimated
Remaining undetected = 8 − 6 = 2 real errors still hiding
Assumption: Testing finds seeded & real errors with the same effectiveness — that's what makes the ratio valid.
Memorize: "Seed known bugs → see what fraction is caught → apply that same fraction to estimate real bugs."

28 Cyclomatic Complexity

McCabe's metric — counts the number of linearly independent paths through code (= minimum test cases needed).
V(G) = E − N + 2P   (E=edges, N=nodes, P=connected components, usually 1)
or simply: V(G) = (number of decision/predicate nodes) + 1
Nodes N=6  (1,2,3,5,6,7)    Edges E=6    P=1
V(G) = 6 − 6 + 2(1) = 2
Independent paths: 1-2-3-6-7 (a>b true) and 1-2-5-6-7 (a>b false) → 2 test cases needed.
Memorize: Complexity = number of decisions + 1. Higher V(G) → harder to test/maintain → consider refactoring if V(G) > 10.

30 Unit Testing (with examples)

Testing the smallest testable piece (function/method/class) in isolation — done by developers, white-box style.

Example

  • Function: add(a, b)
  • Test 1: add(2, 3) → expect 5
  • Test 2: add(-1, 1) → expect 0
  • Test 3: add(0, 0) → expect 0

Key Points

  • Uses stubs (fake called-modules) & drivers (fake calling-modules)
  • Fast, isolated, run constantly during development

Common Tools

  • JUnit (Java) · NUnit (.NET) · PyTest (Python)
Memorize: Smallest scope, done first, done by developers.

31 Integration Testing (with examples)

Tests how integrated modules work together — catches interface & data-passing bugs.
ApproachHow it works
Big BangIntegrate all modules at once, then test
Top-downTest from top module downward, using stubs for missing lower modules
Bottom-upTest from lower modules upward, using drivers for missing upper modules
Sandwich/HybridTop-down + bottom-up combined
Example: "Login" module integrated with "Database" module — verify entered credentials are actually checked against real DB records, not just validated locally.
Memorize: Unit tests one brick; Integration tests the joints between bricks.

32 System Testing (with examples)

Testing the complete, fully-integrated system against the full requirements — done by an independent test team, black-box style.
Example: Testing an entire e-commerce site end-to-end — browse products → add to cart → checkout → pay → receive order confirmation — as one continuous real-world flow.

Key Points

  • Entire application, not individual modules
  • Checks against SRS, not internal code
  • Last technical testing stage before Acceptance Testing
Memorize: System Testing = "does the whole product work as promised?"

34 White Box Testing (with example)

Tests the internal code structure & logic — tester needs access to the source code.

Example

  • Code: if (score >= 40) grade="Pass"; else grade="Fail";
  • Test 1: score=45 → covers the "if" (true) branch
  • Test 2: score=30 → covers the "else" (false) branch
  • Together these give 100% branch/statement coverage of this snippet
Common techniques: Statement coverage · Branch/Decision coverage · Condition coverage · Path coverage · Data flow testing.
Memorize: White box = you can see through the code (glass-box testing).

35 White Box vs Black Box Testing

White BoxBlack Box
Internal code structure is knownInternal code is unknown/irrelevant
Done by developersDone by independent testers
Based on code logicBased on requirements/specifications
Used at Unit & Integration levelsUsed at System & Acceptance levels
Eg: statement/branch coverageEg: boundary value analysis, equivalence partitioning
Memorize: White box = "how" it works internally. Black box = "what" it does for the user.

36 Statement Coverage Technique

Ensures every executable statement in the code runs at least once.
Statement Coverage % = (Statements Executed / Total Statements) × 100

Example

  • Code: read(a,b); if(a>b){ max=a; } print(max);
  • One test case with a=5, b=3 executes every line → 100% statement coverage
  • But it never tests the "a≤b" case — a weakness of this technique
Memorize: Weakest white-box criterion — a line can "pass" even if the logic/branch around it was never truly tested both ways.

37 Condition Coverage

Ensures every individual boolean sub-condition inside a decision evaluates to both True and False at least once.

Example: if (A && B)

TestAB
1TrueFalse
2FalseTrue
Both tests together cover A=T, A=F, B=T, B=F — but note the overall if never evaluated True here, so condition coverage alone doesn't guarantee decision coverage.
Memorize: Statement coverage < Decision coverage < Condition coverage < Multiple-condition coverage — each is stricter than the last.

38 Data Flow Testing Technique

White-box technique that tracks how a variable is defined and later used, testing each def-use path.

Key Terms

  • def — a variable is assigned a value (e.g. x = 5;)
  • c-use — computational use, variable used in a calculation (e.g. y = x + 1;)
  • p-use — predicate use, variable used in a condition (e.g. if (x > 0))
Example: x = read(); if (x > 0) y = x*2; else y = 0; → test cases must exercise the def of x flowing into both its p-use (the if) and its c-use (x*2).
Memorize: "Follow the variable's life — from where it's born (def) to everywhere it's read (use)."

39 Boundary Value Testing (Black Box, with real-life examples)

Bugs cluster at the edges of valid input ranges — so test just below, at, and just above each boundary.

Example: Age field, valid range 18–60

  • Lower boundary: test 17 (invalid), 18 (valid), 19 (valid)
  • Upper boundary: test 59 (valid), 60 (valid), 61 (invalid)
Real life: ATM daily withdrawal limit ₹500–₹40,000 → test ₹499, ₹500, ₹501, ₹39,999, ₹40,000, ₹40,001.
Memorize: "Don't just test the middle — test the edges, that's where off-by-one bugs hide."

41 MTBF vs MTTR

MTBF (Mean Time Between Failures) = Total Uptime / Number of Failures  → higher = more reliable
MTTR (Mean Time To Repair) = Total Repair Time / Number of Failures  → lower = easier to maintain
Numerical: System ran 1000 hrs total, failed 5 times, total repair time = 10 hrs.
Uptime = 1000 − 10 = 990 hrs
MTBF = 990 / 5 = 198 hrs
MTTR = 10 / 5 = 2 hrs
Availability = MTBF/(MTBF+MTTR) = 198/200 = 99%
Memorize: MTBF = how long it lasts. MTTR = how fast it heals.

42 Reverse Engineering (with real-life examples)

Analyzing an existing system to recover its design/architecture — going from code back to design (opposite of forward engineering).

Real-life Examples

  • Studying a 20-year-old undocumented COBOL banking system to rebuild its design before migrating it to Java
  • Decompiling an old .exe to understand undocumented behaviour
  • Analyzing a competitor's app to understand how a feature works
Memorize: Forward engineering: requirements → code. Reverse engineering: code → requirements/design.

45 Regression Testing (with real-life examples)

Re-run existing tests after a change to make sure nothing that used to work is now broken.
Real life: After adding an "Apply Coupon" feature to a shopping cart, re-test Add-to-Cart, Checkout, and Payment flows to confirm they still work.

Key Points

  • Run after every bug fix, patch, or new feature
  • Usually automated — same tests run repeatedly
Memorize: "New code shouldn't break old features" — that's what regression testing checks.

47 Use Case Diagram

Shows functional requirements — actors and the services (use cases) the system offers them.
Memorize: Stick figure = actor, oval = use case, box = system boundary. <<include>> = always happens; <<extend>> = happens only sometimes.

48 Sequence Diagram

Shows objects exchanging messages over time (top → bottom = time passing).
Memorize: Solid arrow = call/request. Dashed arrow = return/response. Vertical dashed line = lifeline (object's existence over time).

49 Activity Diagram

Models a workflow/business process — like a flowchart, but UML-standard.
Memorize: Filled circle = start. Diamond = decision. Circle-with-ring = end. Rounded box = an action.

53 RAD Model (Rapid Application Development)

Emphasizes speed — parallel teams build components quickly using heavy prototyping & reuse, short cycles (60–90 days).

Limits

55 Function Point Analysis (FPA)

Measures software size from the user's point of view, based on 5 function types.
Function TypeMeaning
External Input (EI)Data entering the system (e.g. a form submit)
External Output (EO)Data leaving the system (e.g. a report)
External Inquiry (EQ)Input+output combo with no data stored (e.g. a search)
Internal Logical File (ILF)Data maintained inside the system (e.g. a DB table)
External Interface File (EIF)Data referenced from another system
Memorize: "3 flows in/out/around (EI, EO, EQ) + 2 files (ILF, EIF)" = the 5 FP components.

56 Function Point Calculation — Numerical

UFP (Unadjusted FP) = Σ (count × weight) for each function type
FP = UFP × CAF,   CAF = 0.65 + 0.01 × (sum of 14 General System Characteristics, each rated 0–5)
TypeCountWeight (avg)Total
EI3412
EO2510
EQ248
ILF11010
EIF2714
UFP = 12+10+8+10+14 = 54
Sum of 14 GSC ratings = 35 → CAF = 0.65 + 0.01×35 = 1.00
FP = 54 × 1.00 = 54 Function Points
Memorize: Count the 5 function types with their complexity weights → adjust by CAF → that's your project's FP size (used for effort/cost estimation).

57 Aggregation vs Composition in UML

Both are "has-a" relationships — the difference is whether the part can survive without the whole.
AggregationComposition
Weak "has-a" — part can exist independentlyStrong "part-of" — part's lifecycle depends on whole
Professor still exists if Department is dissolvedRoom is destroyed if the House is demolished
Part can belong to multiple wholesPart belongs to exactly one whole
Hollow diamond ◇Filled diamond ◆
Memorize: Hollow diamond = "can live apart". Filled diamond = "dies together".
